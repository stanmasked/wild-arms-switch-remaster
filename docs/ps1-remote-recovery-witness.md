# Stage 260 — fresh remote recovery-witness proofs over mutual TLS

Previous witness-guarded custody mode required direct read access to the
independent witness SQLite database. This implementation adds a reference
**network-only witness retrieval and verification protocol**:
`tools/audit_record_remote_recovery_witness.py`.

The independently administered witness serves a one-shot mutual-TLS 1.3
request. Its reply contains the **complete authenticated recovery-event
prefix**, witness-chain hash and freshly signed random client request ID.
The custodian checks the pinned TLS leaf certificate, pinned witness
Ed25519 public key, domain-separated signature and every event/hash
before passing the proven prefix to the existing SQLite custody guard.

## Operational setup

Provision the witness with a separate protected SQLite database, a
separate Ed25519 private key, a TLS server certificate and trusted
client CA. Only the witness service reads its own database; never mount
or copy the SQLite file to the custodian server.

Run the independent witness process on a reachable host:

    python3 -m tools.audit_record_remote_recovery_witness serve-once \
      /witness-private/recovery-witness.sqlite \
      /witness-private/signing-key.pem \
      /witness-private/server-cert.pem \
      /witness-private/server-key.pem \
      /witness-private/client-ca.pem PINNED_CUSTODIAN_CLIENT_LEAF_SHA256 \
      --witness-tag independent_wild_arms_witness \
      --host 127.0.0.1 --port 38491

For every custody mutation, run the protected custodian server:

    python3 -m tools.audit_record_custodian_tls serve-once-remote-witness-guarded \
      /custodian-private/anchors.sqlite \
      /custodian-private/signing-key.pem \
      /custodian-private/server-cert.pem \
      /custodian-private/server-key.pem \
      /custodian-private/client-ca.pem PINNED_VERIFIER_CLIENT_LEAF_SHA256 \
      witness.example.invalid 38491 witness.example.invalid \
      /custodian-private/witness-tls-client-cert.pem \
      /custodian-private/witness-tls-client-key.pem \
      /custodian-private/witness-trusted-ca.pem \
      PINNED_WITNESS_SERVER_LEAF_SHA256 \
      /custodian-private/pinned-witness-public.pem \
      PINNED_WITNESS_ED25519_PUBLIC_PEM_SHA256 \
      --custodian-tag wild_arms_custodian_01 \
      --witness-tag independent_wild_arms_witness \
      --host 127.0.0.1 --port 38481

The hostnames and pins above are placeholders, **not a deployed server**.

The existing stage-251/254 client request format for custody reserve and
deposit remains unchanged. When the custody server receives such an
authenticated request, it initiates a **fresh** TLS connection to the
witness. There must be a separately started one-shot witness listener
for each such request. If the service, keys, pins, witness signature,
nonce, or event prefix is invalid, the custody server returns a
generic rejected response and does not commit the write.

Read-only `latest` requests do not need to open a witness connection.

## Freshness and rollback checks

The witness reply signs these fields together with an explicit
domain/version separator: request ID (128-bit randomly generated by the
custodian client), identity tag, event count, final recovery-event digest,
independent witness-chain digest, and **every original event**.

The client requires its exact outstanding request ID. A previously
signed reply from another network query is rejected even if it names
the same history. No client-provided history or server-provided timestamp
can replace the authenticated witness high-water.

The custodian verifies the event prefix and rechecks it under
`BEGIN IMMEDIATE` in its own custody reservation/deposit transaction.
A truncated, forked, or unacknowledged administrative journal prevents
custody mutation. No witness DB is accessed or copied on the custodian.

A current witness proof is a **point-in-time observation**. The witness
may advance after answering but before the custodian's local SQLite
transaction. This stage cannot provide global linearizability or
atomicity across two independently administered databases. It also
cannot guarantee permanent independence of a service that has not been
deployed with appropriately separate operators.

## Adversarial and recovery cases

- Incorrect mutual TLS certificate, CA trust or DER leaf pin: refused.
- Invalid/mismatched pinned Ed25519 witness key: refused.
- Replayed valid witness reply with an old request ID: refused.
- Invalid, truncated or modified recovery-event prefix: refused.
- Witness service offline: custody mutation rejected with no local write.
- Custodian rollback or a newly added but unwitnessed administrative
  event: rejected by its own SQLite writer transaction.
- Existing owned reservation with identical checkpoint/expected head:
  the stage-254 exact retry remains idempotent.
- The witness's **SQLite file never leaves its server**; the returned
  event prefix contains hash commitments, which should remain private.

## Non-goals and limitations

The older custody `serve-once` and locally witness-guarded
`serve-once-witness-guarded` modes remain for compatibility, as do
direct local Python/SQLite calls. Operators must disallow those bypasses
to make this reference network witness mandatory.

There is no production remote witness, persistent service management,
key lifecycle, authenticated external immutable log, cross-system
transaction, third-party audit operator or native Nintendo Switch
gameplay demonstrated here. Only synthetic TLS and SQLite evidence
is tested; original Wild Arms PS1 execution and assets are unverified.

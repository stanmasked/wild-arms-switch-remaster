# Stage413 — conservative derived-address store audit

## Why this stage exists

The verified Stage412 audit found **nine direct LUI/LW reads** of the runtime source-pointer slot at `0x800D2EA0`, but no directly adjacent LUI/store writes. Stage413 extends the *static syntactic evidence* beyond one adjacent pair, without pretending to have reconstructed full executable dataflow.

## Private original executable observations

The privately extracted original `WILDARMS.EXE` identifies as PS-X EXE, with declared text range `0x80011420..0x800D2C20` (exclusive upper bound). The slot `0x800D2EA0` is **640 bytes beyond** that declared text. Its runtime allocation/initialization semantics remain unproven.

The new read-only auditor interprets a narrow set of integer MIPS instructions: `LUI`, `ORI`, `ADDIU`, `ANDI`, `ADD/ADDU`, `OR`, `SLL`, and the conventional register invalidation effects of loads/unknown instructions. It tracks constant register values only within uninterrupted straight-line runs. At each `SB`, `SH`, `SWL`, `SW`, or `SWR`, a candidate destination address is proven **only if the base register remains known** after such limited tracking.

On this original executable the restricted scan gives:

- **0** stores to `0x800D2EA0` with a constant destination proven from the limited straight-line instructions.
- **0** stores with the same 16-bit immediate `0x2EA0` but an unknown base register.
- **27,247** control-transfer resets/delay-slot exclusions during linear scanning.

These are *negative results within one deliberately incomplete static abstraction*. They cannot show that the memory slot is never written. This scan ignores branch-delay instructions, does not prove a control-flow graph, and cannot reconstruct addresses loaded from memory, computed in another function, or passed to memory-copy routines. Some bytes inside declared text may also represent embedded data rather than executable instructions. The full source-file origin remains unknown.

## Reproduce safely on a local copy

```sh
python tools/audit_wild_arms_slot_writes.py /private/path/WILDARMS.EXE \
  > /private/path/stage413-slot-writes.json
python -m unittest discover -s tests -p test_audit_wild_arms_slot_writes.py
```

Outputs are metadata only: counts, limited site offsets and explicit uncertainty flags. Keep the original BIN, EXE, any privately captured logs and game resources outside the public repository.

## Next proof gate

1. Use a trusted PS1 reference emulator/debugger with a **write watchpoint** on `0x800D2EA0..0x800D2EA3`, capturing the program counter, call stack, source register values and most recent file-loading state. No original game bytes belong in public CI.
2. If a writer PC lies inside `WILDARMS.EXE`, correlate that runtime PC against its PS-X EXE text load address. If outside, investigate loaded overlays before identifying the code owner.
3. Observe a concrete transfer call to `0x8002356C`, its actual `a0` value and the file/LBA selection that produced it. Do not infer `CDFLR.BIN` from destination addresses alone.
4. Only then test a local CLUT/pixel decoder against a trusted PS1 reference frame.

No emulation, code execution, images, or proprietary payloads are generated by the Stage413 static tool.
